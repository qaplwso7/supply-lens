# Supply Lens — техническое задание

Статус: решения закрыты, код не начат. Идея и роль в портфеле остаются в `Supply-Lens.md`. Этот документ говорит, что именно строить и в каком порядке.

Дата фиксации: 25 октября 2026. Источники сверены с публичными схемами OSV и deps.dev на эту дату.

## Что делаем

Модель ранжирует популярные пакеты PyPI: у каких из них в ближайшие 90 дней выше шанс публичного advisory с высокой серьёзностью. Раз в неделю security-команда разбирает фиксированное число пакетов с вершины списка. Готовый результат — воспроизводимый датасет, walk-forward отчёт и сравнение порога «под accuracy» с отбором «под недельный бюджет».

## Решения

Эти пункты в `Supply-Lens.md` были открыты. Здесь они закрыты.

| Вопрос | Решение |
| --- | --- |
| Целевая переменная | Публикация advisory по пакету с CVSS v3 ≥ 7.0 либо severity `HIGH` / `CRITICAL`. Горизонт 90 дней. |
| Экосистема | Только PyPI. Поле системы в данных остаётся, чтобы npm можно было добавить тем же кодом. |
| Когорта | 5 000 пакетов, замороженных на старте исследования. |
| Признаки первой версии | История релизов, прошлая история advisory, граф зависимостей на дату решения. |
| Модель | LightGBM. Рядом логистическая регрессия и два правила без обучения. |
| Хранилище | DuckDB и Parquet. Запросы пишутся на SQL. |
| Бюджет ревью | 25 пакетов в неделю. Число задано заранее и на тесте не подбирается. |

Ломающий мажорный релиз в первую версию не входит. На PyPI смена первой цифры версии не означает несовместимое изменение, отдельной разметки breaking changes в открытых данных нет. Одно событие «advisory или мажор» смешало бы два разных механизма в одной метке.

Число мейнтейнеров и частота коммитов в первую версию не входят. В deps.dev их нет. Снимок GitHub «как сейчас» для старой даты решения заглядывает в будущее. Замену активности даёт частота релизов на дату решения.

GitHub API не используем. Advisory из GitHub Advisory Database уже попадают в OSV. Даты релизов PyPI есть в deps.dev как `UpstreamPublishedAt`.

PyTorch не используем. Для редкого события и жёсткого top-N бустинг и честный временной разрез дают ту строку резюме, которая задумана. Линейная модель остаётся, чтобы было с чем сравнить бустинг.

PostgreSQL из черновика идеи заменён на DuckDB: тот же SQL, файл открывается без отдельного сервера, сбор повторяется одной командой. Если позже понадобится именно Postgres в тексте резюме, таблицы переносятся без смены полей.

## Вне первой версии

- npm и любые другие экосистемы.
- Прогноз мажорного или ломающего релиза.
- Сопоставление диапазонов версий OSV с конкретной установленной версией. Метка пакетная: advisory назвал пакет, независимо от того, задета ли последняя версия.
- Признаки из GitHub: мейнтейнеры, коммиты, звёзды «на сегодня».
- Сервис, API, интерфейс, расписание оповещений.
- Полная выгрузка `DependencyGraphEdges`. Таблица огромная, а нужные глубину и число рёбер даёт `Dependencies.MinimumDepth`.

## Постановка

### Единица наблюдения

Строка датасета — пара `(package, decision_at)`.

`decision_at` — время снапшота deps.dev. Из таблицы `Snapshots` берётся один снапшот на календарную неделю, самый ранний в этой неделе. Неделя совпадает с бюджетом «N пакетов в неделю».

Пакет попадает в строку, только если он в замороженной когорте и к `decision_at` у него уже есть релиз с `UpstreamPublishedAt <= decision_at`.

Имена PyPI приводятся к нижнему регистру до любых соединений.

### Когорта

На первом пригодном снапшоте считаем для каждого пакета PyPI число различных пакетов, чей высший релиз напрямую от него зависит. Берём верхние 5 000. Список имён замораживается до конца исследования: пакет, который станет популярным позже, в когорту не добавляется.

Запрос к `Dependents` перед запуском оценивается сухим прогоном BigQuery. Если оценка больше 200 ГБ, когорта берётся из ежемесячного дампа [top-pypi-packages](https://hugovk.dev/top-pypi-packages/) за месяц этого же снапшота, верхние 5 000 по скачиваниям. Запасной источник выбран заранее, чтобы объём запроса не стал новым продуктовым решением.

### Целевая переменная

`y = 1`, если на пакет есть хотя бы одно событие раскрытия:

- экосистема OSV — PyPI;
- `published` попадает в интервал `(decision_at, decision_at + 90 дней]`;
- поле `withdrawn` пустое;
- есть балл CVSS v3 ≥ 7.0, либо при отсутствии балла severity равен `HIGH` или `CRITICAL`;
- алиасы схлопнуты: все записи с одним CVE считаются одним событием. Запись без CVE сохраняет свой OSV id.

`y_critical = 1` при том же правиле и пороге CVSS v3 ≥ 9.0 либо severity `CRITICAL`. Отдельной модели для critical нет. Колонка нужна только стоимости ошибки.

Метка бинарная. Повторные advisory в том же окне не увеличивают `y`.

Advisory без CVSS и без severity `HIGH` / `CRITICAL` метку не ставит. Так из положительного класса выпадают записи о вредоносных пакетах без оценки серьёзности: у них другой механизм, и они могут задавить собой редкие уязвимости кода.

Серьёзность берётся из выгрузки OSV на день скачивания. Истории изменения CVSS в открытом дампе нет. Это принятый остаточный сдвиг: существование advisory фильтруется датой `published`, а вот поздняя смена балла в прошлое не восстанавливается. В README это называется явно.

### Окно обучения

Последние снапшоты, у которых нет полных 90 дней истории после `decision_at`, в датасет не входят: метка для них ещё не созрела.

Минимальная длина обучения — 52 недели решений. Следующие 13 недель — валидация, на ней один раз фиксируются пороги accuracy и F1. Все кварталы после валидации — тест. Итоговая цифра в README считается только по тестовым кварталам.

Между концом обучения и началом теста выбрасываются решения, чьё 90-дневное окно метки пересекает тест. Это purge gap. Без него модель учится на строках, которые уже «видят» начало тестового периода.

Гиперпараметры LightGBM заранее фиксированы и по фолдам не перебираются: `num_leaves=31`, `learning_rate=0.05`, `n_estimators=300`, `min_child_samples=50`, `objective=binary`. Честность разреза важнее подобранного по тесту качества.

Если фаза 0 покажет, что пригодная история короче 52 + 13 + 13 недель, исследование всё равно делается на доступном хвосте, а README пишет фактическую длину. Метку и горизонт из-за короткой истории не меняем.

## Данные

Два источника. Третий клиент не добавляем.

### OSV

Полный дамп PyPI: `https://osv-vulnerabilities.storage.googleapis.com/PyPI/all.zip`.

Из каждой записи сохраняем `id`, `published`, `modified`, `withdrawn`, алиасы, severity / CVSS, имена затронутых пакетов PyPI. Диапазоны версий в первой версии не храним.

OSV — источник истины для метки и для признаков «что уже было известно на дату решения». Запись участвует в признаках только при `published <= decision_at` и пустом `withdrawn`.

### deps.dev

Публичный датасет BigQuery: `bigquery-public-data.deps_dev_v1`.

Нужные таблицы:

- `Snapshots` — календарь решений;
- `PackageVersions` — релизы, `UpstreamPublishedAt`, `VersionInfo`, `ProjectStatus`;
- `Dependencies` — прямые и транзитивные рёбра и `MinimumDepth` для версии пакета;
- `Dependents` — кто зависит от пакета, для когорты и для `direct_dependent_count`.

Литерал системы (`PYPI` или иное) сверяется в фазе 0 запросом `SELECT DISTINCT System`. В коде после этого он записан константой, а не угадан в нескольких местах.

Выгрузка режется по системе, списку снапшотов и списку имён когорты. `DependencyGraphEdges` не читаем. Перед каждым большим запросом — сухой прогон и запись оценки байтов в `notes/feasibility.md`. Результат запроса сохраняется в Parquet, повторно BigQuery не дергается.

Для графовых признаков берётся снапшот с `SnapshotAt = decision_at`, не самый свежий снимок в таблице. Зависимые и рёбра из будущего относительно даты решения — утечка, она допустима только в отдельном эксперименте ниже.

`UpstreamPublishedAt` позволяет восстановить историю релизов из одного снапшота. В признаки версии попадают только те, у которых `UpstreamPublishedAt <= decision_at`. Удалённые с индекса пакеты в позднем снапшоте могут отсутствовать: это смещение выживания, оно описывается в словаре данных и в коде не «лечится» дорисовкой.

### Что считается утечкой

Признак честный, если его можно было посчитать в момент `decision_at`, не зная записей с более поздней датой публикации.

Обязательные проверки в ноутбуке, на всей таблице признаков:

- максимальный `published` среди advisory, вошедших в признаки строки, не больше `decision_at` этой строки;
- у положительной метки есть advisory с `published` строго после `decision_at` и не позже `decision_at + 90 дней`;
- версии в счётчиках релизов опубликованы не позже `decision_at`;
- графовые поля взяты из снапшота, равного `decision_at`.

Отдельный эксперимент обучает ту же модель на честных признаках плюс один заведомо будущий столбец. Столбцы такие:

1. `leaky_advisories_next_90d` — число событий раскрытия внутри окна метки.
2. `leaky_dependents_latest_snapshot` — число зависимых из самого нового снапшота, включая тех, кто появился после решения.
3. `leaky_releases_including_future` — число релизов за 365 дней без отсечения по `UpstreamPublishedAt`.

В отчёте три строчки: честная модель, честная плюс каждый из этих столбцов по отдельности, качество после удаления столбца. Это и есть разбор утечки из будущего для резюме. Если столбец (1) качество не поднимает, соединение метки с признаками собрано неверно, и до текста README пайплайн чинится.

## Признаки

Все признаки считаются на `decision_at`. Пропуски у бустинга остаются пропусками. Для логистической регрессии медиана и масштаб считаются только на обучающей части соответствующего фолда.

Блок без графа:

| Признак | Смысл |
| --- | --- |
| `package_age_days` | Дни от первого релиза до даты решения |
| `days_since_last_release` | Дни с последнего релиза |
| `releases_90d` | Число релизов за 90 дней |
| `releases_365d` | Число релизов за 365 дней |
| `major_bumps_365d` | Сколько раз за 365 дней выросла старшая компонента версии. Непарсящаяся версия даёт 0 |
| `fraction_prerelease_365d` | Доля пререлизов среди релизов за 365 дней |
| `prior_advisories` | Число прошлых событий после схлопывания CVE |
| `prior_high_critical` | Из них с высоким порогом, тем же, что у метки |
| `days_since_last_high_critical` | Дни с последнего такого события. Если их не было — пусто |
| `max_prior_cvss` | Максимальный прошлый CVSS v3. Если баллов не было — пусто |
| `advisories_365d` | Прошлые события за 365 дней |

Блок графа, на версии, которая была высшим релизом на `decision_at`:

| Признак | Смысл |
| --- | --- |
| `direct_dep_count` | Число прямых зависимостей, `MinimumDepth = 1` |
| `transitive_dep_count` | Число различных пакетов в замыкании |
| `max_dep_depth` | Максимальная `MinimumDepth` |
| `direct_dependent_count` | Сколько других пакетов напрямую зависят от этого |
| `deps_with_prior_high_critical` | Сколько прямых зависимостей уже имели высокий advisory к дате решения |

NetworkX считается отдельно, один раз на снапшот, на ориентированном графе прямых зависимостей внутри когорты. Ребро A → B есть, если высший релиз A зависит от любой версии B, и оба имени в когорте. Из него берутся:

| Признак | Смысл |
| --- | --- |
| `pagerank` | PageRank пакета в этом графе |
| `cohort_in_degree` | Входная степень внутри когорты |
| `cohort_out_degree` | Выходная степень внутри когорты |

Граф на 5 000 узлов считается в памяти. Полный граф PyPI в NetworkX не строится.

`ProjectStatus` выгружается как есть. В модель он попадает бинарным `project_inactive`, только если фаза 0 найдёт значение статуса, которое встречается больше чем у 1% строк когорты. Иначе столбец остаётся в сырой выгрузке и в признаки не идёт.

Сравнение «до графа / после графа» — две модели с одними и теми же разрезами: признаки без шести графовых столбцов и полная матрица. Обе честные, без столбцов `leaky_*`.

## Модели и решение

На каждом тестовом квартале сравниваются:

- правило «сначала больше прошлых high/critical, затем больше любых прошлых advisory»;
- правило «сначала больше `direct_dependent_count`»;
- логистическая регрессия scikit-learn на честных признаках, `class_weight="balanced"`;
- LightGBM на честных признаках;
- LightGBM только на блоке без графа.

Политики отбора, пороги которых вообще подбираются, подбираются на валидационном квартале и затем замораживаются:

- порог, максимизирующий accuracy;
- порог, максимизирующий F1;
- бюджет: каждую неделю верхние 25 по убыванию скора, без порога.

Кривые для бюджетов 10 и 50 считаются заранее заданной чувствительностью. Лучшая из трёх в качестве «главного результата» не выбирается.

Метрики по тестовым кварталам, средние и по каждому кварталу отдельно:

- PR-AUC;
- precision@25 на уровне недели: доля разобранных пакетов, у которых `y = 1`;
- полнота событий: доля раскрытий, перед которыми пакет хотя бы раз попал в верхние 25 в пределах предшествующих 90 дней;
- стоимость квартала: `25 * число недель + 5 * пропущенные high + 20 * пропущенные critical`.

Пропуск считается по событию. High — событие с CVSS в `[7.0, 9.0)`, critical — с CVSS ≥ 9.0. Веса 1 / 5 / 20 — сценарий, а не оценка по данным. Рядом та же таблица с весами 1 / 10 / 50, тоже заранее.

Accuracy на редкой метке почти наверняка выберет порог, при котором команда не разбирает почти ничего. Это нужный результат сравнения, его не подменяют другой метрикой, если так вышло.

## Критерий готового проекта

Совпадает с `Supply-Lens.md` и раскладывается на артефакты.

- Команды сборки от дампа OSV и сохранённых выгрузок deps.dev до таблицы признаков. Повторный запуск не обращается к сети, если сырые файлы на месте.
- Словарь полей.
- Ноутбук с walk-forward, purge gap, проверками утечки, таблицей честных и протекающих признаков, сравнением блока без графа и полного блока.

Качество модели порог готовности не определяет. Если бустинг не обходит правило по прошлым advisory, README так и говорит. Это приемлемый итог пет-проекта.

## План

Каждая фаза заканчивается проверяемым результатом. Следующая не начинается, пока он не записан.

### Фаза 0. Проверка, что метку из чего собрать

Данных в репозитории ещё нет. Это ближайшая работа.

1. Скачать дамп OSV PyPI и посчитать по годам число событий после схлопывания CVE: все, high/critical, critical. Отдельно — сколько различных имён пакетов.
2. Запросом к `Snapshots` записать минимальную дату, максимальную дату и число снапшотов. Литерал системы PyPI записать рядом.
3. Оценить сухим прогоном запрос когорты. Выбрать источник когорты по правилу из раздела «Когорта».
4. По замороженной когорте посчитать число событий high/critical и долю строк `(package, week)` с `y = 1` на доступной истории. Пока граф не нужен: хватает календаря снапшотов и OSV.

Результат фазы — `notes/feasibility.md` с этими числами и одной строкой решения.

Запасной ход, если различных событий high/critical по когорте меньше 200: в положительный класс добавляется severity `MEDIUM` и CVSS ≥ 4.0. Полнота по high/critical всё равно считается отдельно. Горизонт, когорта и бюджет при этом не меняются. Других развилок у фазы 0 нет.

### Фаза 1. Датасет

1. Разобрать OSV в таблицы `advisories` и `advisory_packages`.
2. Выполнить SQL deps.dev и сохранить Parquet: версии когорты, прямые и транзитивные зависимости высших релизов, число прямых зависимых.
3. Собрать таблицу признаков и метки. Посчитать PageRank по снапшотам.
4. Прогнать четыре проверки утечки из раздела «Что считается утечкой».
5. Написать словарь полей.
