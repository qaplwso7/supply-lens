# Supply Lens

Статус: идея зафиксирована. Решения и план работ — в `TZ.md`. Реализация не начата.

Роль в портфеле: исследование данных и обучение модели.

## Бизнес-суть

Команде разработки нужно заранее видеть, у каких библиотек в ближайшие 90 дней выше шанс серьёзной уязвимости или ломающего мажорного релиза. Тогда обновление планируют до инцидента, а не после него.

Пользователь результата: платформенная или security-команда, у которой есть недельный бюджет на ревью ограниченного числа пакетов.

## Источник данных

Живые открытые источники, без синтетики:

- OSV (https://osv.dev, API https://api.osv.dev) — база уязвимостей.
- deps.dev (https://docs.deps.dev) — граф зависимостей и метаданные пакетов.
- GitHub Advisory Database и история релизов через GitHub API.

Рабочий срез: 5–10 тысяч популярных пакетов PyPI и npm. Этого достаточно для пет-проекта.

## Архитектура и стек

- Сборщик на Python складывает снапшоты пакетов в PostgreSQL.
- Признаки: возраст релиза, частота коммитов, число мейнтейнеров, история advisory, глубина и ширина графа зависимостей (NetworkX).
- Модель: LightGBM или небольшой классификатор на PyTorch.
- Валидация только walk-forward: обучение на прошлом, проверка на будущем.
- Порог выбирается под ограничение «security успевает разобрать N пакетов в неделю», с отдельной ценой пропуска высокого severity.
- Базовый стек: Python, Pandas, SQL, scikit-learn или PyTorch.

## Киллер-фича для резюме

Честный разбор утечки из будущего и цена ошибки. В ноутбуке и в README должно быть видно:

- какие признаки подсматривают вперёд;
- как падает качество после их удаления;
- как порог оптимизирован под бюджет ревью, а не под accuracy.

## Строка в резюме

Собрал временной датасет из OSV и deps.dev и построил модель риска зависимостей с walk-forward валидацией и порогом под недельный бюджет security-ревью.
