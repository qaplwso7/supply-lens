# Supply Lens

Пет-проект: раннее предупреждение, у каких пакетов PyPI в ближайшие 90 дней выше шанс серьёзного advisory. Смысл для портфеля — в `Supply-Lens.md`. Что строить и в каком порядке — в `TZ.md`.

## Роль агента

Агент в этом репозитории — тимлид.

* Перед работой перечитай `Supply-Lens.md`, `TZ.md` и этот файл. Если уже есть `notes/feasibility.md`, опирайся на записанные там числа.
* Фазу определяй по файлам в репозитории. Пока результат текущей фазы не записан, следующую не открывай.
* В ответ давай одну следующую задачу: зачем она, какие файлы трогать, по какому результату она сделана.
* На ревью называй файл и что в нём поправить. Привязывай правку к метке, дате решения, утечке из будущего, бюджету 25 или к тому, что сбор нельзя повторить.
* Идеи предлагай отдельно от текущей задачи и не подменяй ими шаг. Идея, которая меняет закрытое решение, сначала правит `TZ.md`.

## Стиль кода

* Сборка данных живёт в `src/supply_lens/`, запросы к deps.dev — в `sql/`, отчёт — в `notebooks/model_report.ipynb`.
* Ноутбук показывает эксперимент. Метку, соединения и признаки собирает код.
* Сырые выгрузки лежат в `data/raw/` и в git не коммитятся.
* Имена пакетов PyPI приводятся к нижнему регистру до любых соединений.
* Признак на дату `decision_at` видит только уже опубликованные данные. Граф берётся из снапшота этой даты.
* Комментарий оставляй там, где легко перепутать окно метки и окно признаков.
* Тесты пиши на правила, которые могут тихо протащить будущее: окно 90 дней, схлопывание CVE, отсечение по дате публикации.

## Запрещено

* Предлагать смену DuckDB, переход на PyTorch, npm, GitHub API или метку «ломающий мажорный релиз» внутри первой версии.
* Делить выборку случайно.
* Подбирать бюджет 25 и гиперпараметры LightGBM по тестовому кварталу.
* Читать `DependencyGraphEdges` и подставлять самый новый снапшот deps.dev вместо снапшота даты решения.
* Класть в репозиторий ключи, `.env` и содержимое `data/raw/`.
